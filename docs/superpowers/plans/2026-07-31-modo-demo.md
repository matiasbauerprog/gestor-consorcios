# Modo Demo — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Una versión demo pública del sistema, linkeable desde la web comercial, con 6 meses de datos realistas, entrada por selector de rol sin credenciales y reset automático cada 6 horas.

**Architecture:** Mismo codebase que producción, con un flag `DEMO_MODE` que activa un endpoint de login sin credenciales (protegido por tres candados anti-producción) y cambia comportamientos de UI. El dataset lo genera `backend/seed_demo.py`, derivado de `seed_e2e.py`, que puebla la app a través de su propia API con `TestClient` in-process — así el dataset es consistente por construcción y el generador funciona como test end-to-end de 6 meses de operación.

**Tech Stack:** Python 3 · FastAPI · SQLAlchemy 2.0 · pydantic-settings · pytest · React + Vite · Railway (deploy + cron) · GitHub Actions (mirror).

**Spec:** `docs/superpowers/specs/2026-07-30-modo-demo-design.md`
**Branch:** `feature/modo-demo` (ya creada, con el spec commiteado)

## Global Constraints

- **OpenAPI-first** (`.claude/rules/openapi-first.md`): todo endpoint nuevo se documenta en `openapi.yaml` **antes** de escribir el router. Path params con nombre completo del recurso, nunca `{id}`.
- Cada operación FastAPI declara `response_model` y `status_code` explícitos.
- **Identidad y rol salen del token, nunca del body** (`.claude/rules/security.md`).
- Nunca hardcodear credenciales: van por variables de entorno.
- Tests: un archivo por router en `tests/test_<recurso>.py`. Validaciones de schema se asertan con **400**, no 422 (`backend/main.py` convierte `RequestValidationError`).
- Frontend: HTML semántico, un solo `<main>` por pantalla, colores vía `var(--color-*)` — nunca hex hardcodeado. Mobile-first, usable a 375px, targets táctiles ≥44px.
- Comando de tests: `./.venv/Scripts/python.exe -m pytest -v` (Windows con venv).
- Ejecutar backend: `uvicorn backend.main:app --reload`.

    def _demo_mode_requiere_db_demo(self) -> "Settings":
        """Candado anti-producción.

        Con DEMO_MODE=true se registra POST /auth/demo-login, que emite tokens
        sin pedir credenciales. Si ese flag se activara por error contra la base
        de producción sería un bypass total de autenticación, así que exigimos

            raise ValueError(
                "DEMO_MODE=true exige una DATABASE_URL que contenga 'demo' "
                f"(recibida: {self.DATABASE_URL!r}). Es un candado "
                "anti-producción: el modo demo emite tokens sin credenciales."
            )
        return self

A diferencia de `backend/seed.py` (fixture de smoke-test que escribe directo a
la DB), este módulo puebla la app **a través de su propia API** con TestClient

        python -m backend.seed_demo [--reset]

PISOS_DEMO = 3                      # 3 pisos × 6 unidades (A–F) = 18 UF
DOMINIO_DEMO = "demo.local"
EMAIL_ADMIN_DEMO = "admin@demo.local"
NOMBRE_CONSORCIO = "Edificio Libertador"

# Deptos pinneados: son los destinos del selector de rol de /auth/demo-login.
CODIGO_PUNTUAL_FIJO = "UF-01A"
CODIGO_MOROSO_FIJO = "UF-03C"


def meses_demo(hoy: date, cantidad: int = 6) -> list[str]:
    """Los `cantidad` meses calendario completos anteriores al mes en curso.

    Corriendo el 2026-07-31 → ['2026-01' … '2026-06'].
    El mes en curso queda abierto a propósito: el visitante tiene un período
    vivo donde cargar gastos y probar el cierre él mismo, que es la acción más
    demostrativa del sistema.
    """
    meses: list[str] = []
    anio, mes = hoy.year, hoy.month
    for _ in range(cantidad):
        mes -= 1
        if mes == 0:
            anio, mes = anio - 1, 12
        meses.append(f"{anio:04d}-{mes:02d}")
    return list(reversed(meses))


def perfiles_deterministas(deptos: list[dict]) -> tuple[list[dict], list[dict], list[dict]]:
    """Reparte los deptos en (puntuales, irregulares, morosos) sin azar.

    `seed_e2e.py` mezcla con RNG.shuffle antes de asignar perfiles. Para el demo
    eso no sirve: el selector de rol apunta a emails fijos, así que qué depto es
    moroso tiene que estar pinneado y ser estable entre corridas.

    Mantiene la distribución 70/15/15 del original, que sobre 18 UF da 12/3/3.
    """
    por_codigo = {d["codigo"]: d for d in deptos}
    n = len(deptos)
    corte_punt = int(n * 0.70)
    corte_irr = int(n * 0.85)

    fijo_puntual = por_codigo.get(CODIGO_PUNTUAL_FIJO)
    fijo_moroso = por_codigo.get(CODIGO_MOROSO_FIJO)
    pinneados = {d["codigo"] for d in (fijo_puntual, fijo_moroso) if d is not None}

    # Orden estable por código, con los pinneados fuera del reparto.
    resto = [d for d in sorted(deptos, key=lambda x: x["codigo"])
             if d["codigo"] not in pinneados]

    puntuales = ([fijo_puntual] if fijo_puntual else []) + resto[: corte_punt - (1 if fijo_puntual else 0)]
    usados = len(puntuales) - (1 if fijo_puntual else 0)
    irregulares = resto[usados: usados + (corte_irr - corte_punt)]
    usados += len(irregulares)
    morosos = ([fijo_moroso] if fijo_moroso else []) + resto[usados:]

    return puntuales, irregulares, morosos

### Task 7: Reset por cron sobre Postgres

**Esta task cambió de forma respecto del plan original.** El plan decía: cron cada
6 h *más* seed automático al bootear si la base está vacía, condicionado a que el
generador tardara ≤60 s. **La medición de la Task 4 dio 67-69 s**, así que el
seed-on-boot queda descartado (haría fallar el healthcheck de Railway durante el
arranque).

Y al bajar a cron surgió un problema que el plan no anticipaba: en Railway los
cron jobs corren como contenedores separados y los volúmenes se montan en un solo

mientras el web atiende es receta de bloqueos.

como contenedor aparte y se conecta por red. Beneficios laterales: iguala a
producción, `psycopg2` ya está en `requirements.txt`, y no hay downtime durante el
reset.

```jsx
import { useState } from "react";
import { useNavigate } from "react-router-dom";
import { demoLogin } from "../api/demo";
import { useAuth } from "../auth/AuthContext";

const ROLES = [
  {
    rol: "administracion",
    titulo: "Administración",
    detalle: "Cargá gastos, cerrá períodos y liquidá al encargado.",
  },
  {
    rol: "propietario_al_dia",
    titulo: "Propietario al día",
    detalle: "Mirá tu saldo, presentá un pago y reservá el SUM.",
  },
  {
    rol: "propietario_moroso",
    titulo: "Propietario moroso",
    detalle: "Vas a ver los intereses aplicados y el reclamo.",
  },
];

export default function DemoLogin({ onSinDemo }) {
  const { login } = useAuth();
  const navigate = useNavigate();
  const [cargando, setCargando] = useState(null);
  const [error, setError] = useState(null);

  async function entrar(rol) {
    setError(null);
    setCargando(rol);
    const r = await demoLogin(rol);
    setCargando(null);

    if (r.status === 200) {
      await login(r.data.access_token, r.data.user);
      navigate("/", { replace: true });
      return;
    }
    if (r.status === 404) {
      // El backend no corre en modo demo: caer al login normal.
      onSinDemo?.();
      return;
    }
    if (r.status === 503) {
      setError("El demo se está regenerando. Probá de nuevo en un minuto.");
      return;
    }
    setError("No pudimos entrar al demo. Intentá de nuevo.");
  }

  return (
    <main className="login-page">
      <section className="login-card demo-selector">
        <h1>Gestión de Consorcios</h1>
        <p className="login-subtitle">Probá el sistema como:</p>

        {ROLES.map(({ rol, titulo, detalle }) => (
          <button
            key={rol}
            type="button"
            className="demo-rol"
            onClick={() => entrar(rol)}
            disabled={cargando !== null}
          >
            <strong>{titulo}</strong>
            <span>{cargando === rol ? "Entrando..." : detalle}</span>
          </button>
        ))}

        {error && <p role="alert" className="login-error">{error}</p>}

        <p className="demo-aviso">
          Demo público: los datos se reinician cada 6 horas. Podés crear, editar
          y borrar sin miedo.
        </p>
      </section>
    </main>
  );
}
```

- [ ] **Step 4: Crear el workflow de mirror**

Creá `.github/workflows/mirror-demo.yml`:

```yaml
name: mirror-demo

# Espeja el estado ACTUAL del repo al repositorio publico del demo como un
# unico commit huerfano. Nunca espeja el historial: hay commits viejos con
# consorcio.db.corrupta (base SQLite con hashes de password).
on:
  push:
    branches: [master]
  workflow_dispatch:

jobs:
  mirror:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 1

      - name: Publicar snapshot
        env:
          MIRROR_TOKEN: ${{ secrets.MIRROR_TOKEN }}
          MIRROR_REPO: ${{ vars.MIRROR_REPO }}
        run: |
          set -euo pipefail
          test -n "$MIRROR_TOKEN" || { echo "Falta MIRROR_TOKEN"; exit 1; }
          test -n "$MIRROR_REPO"  || { echo "Falta MIRROR_REPO";  exit 1; }

          # Cinturon y tiradores: si el snapshot incluye una base, abortar.
          if git ls-files | grep -iE '\.(db|sqlite|corrupta)$'; then
            echo "ERROR: el snapshot incluye archivos de base de datos"
            exit 1
          fi

          rm -rf .git
          git init -q
          git config user.name "mirror-bot"
          git config user.email "mirror-bot@users.noreply.github.com"
          git add -A
          git commit -q -m "snapshot: $GITHUB_SHA"
          git branch -M master
          git push -q --force \
            "https://x-access-token:${MIRROR_TOKEN}@github.com/${MIRROR_REPO}.git" master
```
